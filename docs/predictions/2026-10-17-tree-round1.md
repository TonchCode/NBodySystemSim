What §0.4 already says about the mechanism, and which the predictions build on: the per-pop
SIMT efficiency is fine (0.64 / 0.85), but at interaction sites only 3–4 lanes are active
(0.09 / 0.12). The leaf-bucket loop (up to 16 interactions) is run by the few lanes that reached
a bucket in that iteration, while the lanes that accepted a cell (1 interaction) or opened a node
(0) wait. A back-of-envelope decomposition of the 8192 counts (pops ≈ 1 + 2 × opens; ≈ 40% of
pops accept, ≈ 10% are buckets of ≈ 12) gives eff ≈ 0.12 with *perfect* per-iteration
reconvergence. So the low number is the structure of the naive walk, not a compiler pathology,
and sorting cannot fix it. That bounds what #5 can gain from divergence alone.

## 1. Protocol (fixed now)

`tools/capture_env.ps1` before and after, into `results/<date>_tree_round1/`. Close background
GPU load. Every tree run: `--leaf 16 --block 128 --warmup-ms 300 --runs 11`, `--batch 5` for
N ≤ 65536, else 1; validation on (`--fp64-sample 512`); `--tree-stats` CSV per run.

| set | runs |
|---|---|
| **A, main grid** | {bh_naive, bh_sorted, bh_hilbert} × {plummer, collision, core} × N ∈ {65536, 262144, 1048576}, θ = 0.5 (27 runs) |
| **B, timelines** | {bh_naive, bh_sorted} × {plummer, core} × N ∈ {65536, 1048576}, θ = 0.5, `--timeline --timeline-launches 5` → `timeline_analysis.py` |
| **C, θ sweep** | {bh_naive, bh_sorted} × plummer, N = 262144, θ ∈ {0.3, 0.5, 0.7, 1.0}; plus θ = 0 at **N = 65536** (an exact walk of N² interactions; at 262144 that would be 6.9e10 interactions in one launch, too close to the TDR limit) |
| **D, crossover** | {bh_naive, bh_sorted} plummer θ = 0.5 at N ∈ {8192, 16384, 24576, 32768, 49152, 65536}. Best all-pairs at the same N (rule 8): max over `allpairs_tuned` b128 u0 and `allpairs_multi` b ∈ {128, 256, 512, 1024} × q ∈ {1, 2, 4, 8, 16}, same flags. At N ∈ {262144, 524288}: tuned b128 u0, multi b128 q2, multi b256 q4 (the round-2 winners at 65536). **N = 1M all-pairs is not run** (≈ 0.9 s per launch); it is extrapolated as 4 × T(524288) and labelled [D]. |

Times are medians. "Traversal" = the traverse phase from the event launches; "build" = keys +
sort + tree phases; "total" = the production pipeline median (no events). Speedups #5/#4 are
on the traversal phase *and* on the total (maeda2026gtap: report phase and end to end
separately).

## 2. Work per body (P-T1), θ = 0.5

BH work grows as log N [P:barnes1986hierarchical: O(N log N)]. From the 8192 point (951) and
≈ 2.3 octree levels more at 1M, with part of the 951 being the N-independent leaf/near field:

| IC | N = 65536 | 262144 | 1048576 |
|---|---|---|---|
| plummer, interactions/body | **1200** (950–1450) | **1400** (1100–1700) | **1600** (1250–1950) |
| collision / plummer | 0.95 (0.8–1.1) | 0.95 (0.8–1.1) | 0.95 (0.8–1.1) |
| core / plummer | 1.15 (1.0–1.4) | 1.15 (1.0–1.4) | 1.15 (1.0–1.4) |

- P-T1a: interactions/body increases monotonically with N for every IC.
- P-T1b: interactions/body is identical (exactly) for the three variants (same tree, same walk).
- Collision: each body mostly resolves its own half-mass sphere (≈ Plummer of N/2) and sees the
  other as a few cells. Core: core bodies resolve a very dense N/4 Plummer plus the halo, halo
  bodies see the core as one cell; mean slightly above Plummer, bimodal.

## 3. Build vs traversal time, θ = 0.5, Plummer (P-T2, P-T3)

Rates: at 8192 a starved launch did 10.5 / 15.3 G interactions/s with 4 warps on 64 SMs. In the
latency-bound regime the rate grows ≈ linearly with resident warps, up to an issue/memory
ceiling. Issue model [D]: ≈ 17.4 slots per interaction / (32 × SIMT eff) + ≈ 25 slots per pop /
(32 × pop eff) × 0.61 pops per interaction → ≈ 5.1 slots per interaction for #5 and 6.8 for #4,
i.e. ≈ 170 and 125 G interactions/s at 80 SMs × 4 issue/clk × 2.7 GHz. #4 is expected to sit
below its issue ceiling, limited by scattered L2 loads (up to 32 sectors per warp load).

| N | traversal rate #4 / #5 (G int/s) | traversal ms #4 | traversal ms #5 | build ms (keys+sort+tree) | Hilbert "order" ms |
|---|---|---|---|---|---|
| 65536 | **70 / 130** | **1.1** (0.6–2.0) | **0.60** (0.33–1.1) | **0.20** (0.10–0.40) | **0.14** (0.07–0.30) |
| 262144 | **55 / 160** | **6.7** (3.7–12) | **2.3** (1.3–4.2) | **0.26** (0.13–0.52) | **0.17** (0.08–0.35) |
| 1048576 | **45 / 160** | **37** (20–67) | **10.5** (5.8–19) | **0.55** (0.27–1.1) | **0.35** (0.17–0.70) |

- **P-T2 (build is small and shrinks):** build / total for #5 = **25% (10–45%) at 65536, 10%
  (4–20%) at 262144, 5% (2–10%) at 1M**. For #4: 15%, 4%, 1.5% (each ×/÷ 2.5). The sort is
  the largest build phase at every N (P-T2b).
- **P-T3 (the traversal rate is far below all-pairs):** the best tree rate (#5, any N) is
  **≤ 15% of the best all-pairs rate** (≈ 1266 G/s): ≤ 190 G interactions/s. This is the
  quantitative form of "traversal maps poorly onto SIMT cores" [P:nagarajan2025rtbarneshut,
  motivation only]. The tree wins on work, not on rate.
- P-T3b: the #4 rate does not increase from 262144 to 1M (the per-SM working set leaves L1);
  the #5 rate changes by ≤ 15% between 262144 and 1M.

Collision and core: traversal time = Plummer time × (their interactions/body ratio, §2) ×
(1.0–1.3 for core #4, which pays most for the bimodal mix). Build time within ±20% of Plummer
at the same N, except the tree phase for core (+0–40%, depth 43 vs 31: longer bottom-up chains).

## 4. Crossover vs the best all-pairs (P-T4)

Model [D]: tree total(N) = build(N) + N·I(N)/R(N), with R growing ≈ linearly with N up to the
§3 plateau (R5 ≈ min(160, 19·N/8192), R4 ≈ min(70, 13·N/8192) G/s, the 8192 point warmed by
≈ 1.25×); all-pairs = N² / R_ap(N), R_ap ≈ 1150–1270 G/s from round 2.

| | prediction |
|---|---|
| **P-T4a: crossover N, bh_sorted vs best all-pairs** | **≈ 28,000 (16,000–48,000)**: at 16384 all-pairs is still ≈ 3× faster, at 32768 the tree wins by ≈ 1.3× |
| **P-T4b: crossover N, bh_naive** | **≈ 34,000 (20,000–64,000)**, and N_x(#4) ≥ N_x(#5) |
| P-T4c: total speedup of bh_sorted over the best all-pairs | 65536: **4.2×** (2–8); 262144: **21×** (10–40); 1M: **≈ 80×** (40–160) [D, all-pairs extrapolated] |
| P-T4d: total speedup of bh_naive over the best all-pairs | 65536: **2.6×** (1.2–5); 262144: **8×** (4–16); 1M: **≈ 23×** (11–46) [D] |

The crossover is located by linear interpolation of log(T_tree/T_ap) between the bracketing N of
set D.

## 5. Imbalance metrics, #4 vs #5 (P-T5), θ = 0.5

Definitions: `docs/03-design.md` §14. Values are for the traversal kernel.

| metric | IC | N | #4 bh_naive | #5 bh_sorted (Morton) |
|---|---|---|---|---|
| per-warp max/mean (interactions) | plummer | 65536 / 262144 / 1M | **1.30 (1.22–1.40)** at each N | **1.10 / 1.08 / 1.07** (each ±0.05) |
| | collision | all three | 1.30 (1.20–1.42) | ≤ 1.12 |
| | core | all three | **1.45 (1.30–1.70)** | ≤ 1.12 |
| SIMT eff, interaction sites | plummer | all three | **0.09 (0.06–0.12)** | **0.13 / 0.14 / 0.15** (each 0.10–0.25) |
| SIMT eff, pops | plummer | all three | **0.65 (0.55–0.75)** | **0.88 / 0.90 / 0.91** (each ±0.06) |
| warp-cost max/mean | plummer | 1M | 1.15 (1.05–1.30) | **1.4 (1.2–1.8)** |
| | core | 1M | 1.2 (1.05–1.4) | **2.0 (1.4–3.0)** |

Directional, all ICs and N:
- **P-T5a:** #5 per-warp max/mean < #4's, and #5's decreases with N (a warp of 32 Morton
  neighbours covers a smaller region at higher density).
- **P-T5b:** #5 SIMT efficiency (both sites) > #4's, but **#5 interaction-site efficiency stays
  ≤ 0.25** at every N and IC. Sorting does not remove the leaf-bucket serialization (§0 note).
- **P-T5c:** #5 warp-cost max/mean > #4's. Sorting moves the imbalance from inside warps to
  between warps (dense-region warps are uniformly expensive).
- **P-T5d (Hilbert vs Morton):** Hilbert per-warp max/mean ≤ Morton's at every N and IC, by
  0.5–3% [P:thaler2026sfcneighbor: Hilbert compactness; Morton has jumps, so some Morton warps
  span two separated regions].

## 6. #5 / #4 speedup (P-T6)

| IC | N = 65536 | 262144 | 1M |
|---|---|---|---|
| plummer, traversal | **1.9×** (1.3–3.5) | **2.9×** (1.6–5) | **3.5×** (1.8–6) |
| plummer, total | 1.7× (1.2–3) | 2.7× (1.5–4.8) | 3.4× (1.8–6) |
| collision, traversal | 1.9× (1.3–3.5) | 2.9× (1.6–5) | 3.5× (1.8–6) |
| core, traversal | 2.2× (1.4–4) | 3.3× (1.8–6) | **4.0×** (2–7) |

- **P-T6a:** the speedup grows with N (more of #4's node loads miss L1; #5's stay warp-uniform).
- **P-T6b:** core ≥ plummer at each N (the bimodal mix hurts #4's warps most).
- **P-T6c (decomposition):** the speedup is larger than the SIMT-efficiency ratio alone predicts:
  traversal speedup / (eff_inter #5 / eff_inter #4) ≥ 1.3 at 1M Plummer. Divergence (≈ 1.6×
  by the 32/k model [P:dale2026warpdivergence, T2]) explains only part; the rest is memory
  coalescing (one sector per warp load instead of up to 32).
- **P-T6d (Hilbert):** Hilbert traversal time = Morton's within ±5%. Its extra order phase
  (§3) makes the Hilbert *total* slower than Morton's at 65536 (by 10–25%) and within ±5% at 1M.

## 7. SM-level imbalance, timelines (P-T7), θ = 0.5, traversal kernel

512 blocks at 65536 fit in one wave (960 slots, 6–7 blocks per SM): every block starts at t ≈ 0,
so block-cost variance shows up directly as tail. At 1M (8192 blocks, 8.5 waves) dynamic refill
should smooth it (§8.1: multi q4 had a 0.1% tail with refill).

| IC | N | metric | #4 | #5 |
|---|---|---|---|---|
| plummer | 65536 | SM efficiency | **0.90 (0.80–0.97)** | **0.80 (0.65–0.92)** |
| core | 65536 | SM efficiency | 0.88 (0.75–0.96) | **0.70 (0.50–0.85)** |
| plummer, core | 1M | SM efficiency | ≥ 0.93 | ≥ 0.93 |
| plummer, core | 1M | tail % of span | ≤ 5 | ≤ 5 |

- **P-T7a:** at 65536, SM efficiency #5 < #4 for both ICs. The same mechanism as P-T5c, seen at
  the SM level: Morton blocks in the dense core are the last to finish.
- **P-T7b:** at 1M the refill removes it: |SM eff #5 − SM eff #4| ≤ 0.04.
- P-T7c: no idle SMs at 65536 or 1M (512 and 8192 blocks).
- The instrumented twin runs 5–40% slower than production (counter and leader code). Its
  timelines are used for structure only (D-011).

## 8. Force error and cost vs θ (P-T8), Plummer, N = 262144

Errors are bitwise identical for #4 and #5 (P-T1b), so they are measured once per θ. The
θ = 0.5 value is known (§0.4–5: rms 6.6–7.1e-3), so it is not scored.

| θ | rms rel (scored range) | p99 rel | interactions/body ÷ the θ = 0.5 value | gates |
|---|---|---|---|---|
| 0 (run at N = 65536) | D-009 normMax ≤ 1.0·u·√N | — | exactly N per body | **D-009 PASS** |
| 0.3 | **1.9e-3** (1.2e-3–3.0e-3) | 5e-3 (3e-3–8e-3) | **3.2** (2.3–4.6) | TG PASS |
| 0.5 | (known ≈ 6.7e-3) | (known ≈ 1.8e-2) | 1 | TG PASS |
| 0.7 | **1.5e-2** (1.1e-2–2.2e-2) | 4e-2 (2.5e-2–6e-2) | **0.45** (0.33–0.60) | TG PASS |
| 1.0 | **3.6e-2** (2.2e-2–6e-2) | 9.5e-2 (5e-2–0.18) | **0.19** (0.12–0.30) | TG PASS |

- **P-T8a:** log-log slope of rms error over θ ∈ {0.3, 0.5, 0.7}: **2.5 (2.0–3.0)**. The
  monopole error per cell is ∝ (bmax/d)² ≤ θ², and the error grows faster than θ² because larger
  θ also accepts cells closer to the body [D].
- **P-T8b:** log-log slope of interactions/body over the same θ: **−2.4 (−3.0 to −1.8)**
  (opening-sphere volume ∝ θ⁻³, softened by the N-independent leaf part).
- **P-T8c:** at θ = 0.5, collision and core rms errors are within 0.6–1.6× of Plummer's.
- **P-T8d:** every run in sets A–D passes its gates (TG1/TG2 for θ > 0, D-009 for θ = 0 and the
  all-pairs runs), with zero stack overflows.
- **P-T8e (control, θ = 0, N = 65536):** nothing is ever accepted, so every body walks the
  *identical* path (all nodes, all buckets, same order) and there is no imbalance to fix.
  Prediction: bh_naive and bh_sorted traversal times are **equal within ±5%**, SIMT efficiency
  (both sites) **≥ 0.9** for both, per-warp max/mean = 1.000. If #5 is still faster here, its
  gain at θ > 0 is not (only) about divergence. This is the "only the order differs" control.
- Error vs time is reported as a curve over θ, not a single point [P:madan2025stochastic: error
  vs time as the comparison axis for GPU Barnes-Hut].
