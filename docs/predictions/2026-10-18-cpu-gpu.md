## 0. Observed while building (before this file; NOT measurements, not scored as evidence)

Everything here comes from correctness runs, the selftest and one functional run per new path at
N = 8192 (Plummer, 3 runs, 2 warm-up launches, a GPU that was not checked for idle), so the reader can
see what the ranges below could have been anchored on.

1. **SASS:** 222 of 222 pre-existing functions identical; 3 new (`allPairsRangeKernel<128|256>`
   40 regs, 0 spills; `scatterSlotsKernel` 14 regs). `phase1/sass_diff.txt`.
2. **CPU topology** [M]: 6 P-cores (LPs 0–11, two per core) + 8 E-cores (LPs 12–19). `--cpu-info`, one
   run: dependent-chain clock 5.00 GHz with one LP per P-core busy (4.90–5.08), 4.66 GHz with all 12 P LPs
   busy, 3.86 GHz on the 8 E-cores, and P 4.61 / E 3.72 GHz with all 20 busy (one thread at 2.87: an LP
   shared with the dispatcher). LP 0 alone: 4.48 GHz. Power plan: a custom "Ultimate" plan; no Windows
   power-mode overlay applies. CPU temperature: not readable without admin.
3. **`_mm256_rsqrt_ps` gives the same bits on a P-core and an E-core** for 2²⁰ inputs.
4. **The host tree is the GPU tree bit for bit**: 8 ICs × 2 mass spectra at N = 10007, 65536 and 1M
   (`phase1/tree_compare_1M.txt`). The first build had the COM FMA operands reversed (my SASS reading);
   the comparison caught it (13,021 of 65,535 nodes off by 1 ulp at 65536).
5. **Selftest PASS**: 7840 exact lattice cases (602 new CPU/hybrid), 2563 new R3 #8 checks, 0 failures;
   `--selftest-drop 5` detects 6720 of 6720 visible drops. CPU vs GPU walks: worst |Δa|/Σ|f| = 0.125 of
   the (2I + 64) u bound. At N = 65536 the CPU rsqrt path has normMax = 0.38 u√N, the same as naive's 0.38.
6. **Functional runs, N = 8192** (`phase1/functional/`; host clock):
   - `cpu_allpairs` (20 workers, dynamic): 1.86 ms ≈ **36 G int/s**; worker busy max/mean 1.19;
     **77.7% of the items done on P workers**.
   - `cpu_bh` (G = 32, leaf 16): build 0.38 ms (keys 0.06, sort 0.20, tree 0.13), traversal 0.61 ms
     (1.35e7 interactions, **22 G int/s**); per-slot counts = `bh_warp`'s.
   - `cpu_bh_scalar`: traversal 2.79 ms (7.8e6 interactions, **2.8 G int/s**), so the group walk is
     **4.6× faster in time** while doing 1.73× the interactions.
   - `hyb_phase` 0.35 ms and `bh_warp_refit` (K = 8) 0.34 ms, both bitwise `bh_warp`.
   - Dynamic `hyb_allpairs` / `hyb_bh` dropped the CPU at 8192 after the probe (CPU share below the
     minimum).
   - Pinned copies of 16 B/body (128 KB): D2H 0.013 ms, H2D 0.026 ms.
7. **Two pool defects found and fixed before this file:** a start-up race (a worker could miss the first
   job: hang), and spin starvation of the unpinned dispatcher. The latter made the CPU sort at 8192 take
   2.9 ms; 0.20 ms after the fix.

## 7. Phase-2 protocol (pre-registered)

- `tools/capture_env.ps1` and `tools/capture_cpu_env.ps1` before and after, with GPU idle ≤ 5% and the idle
  CPU utilisation recorded. The screensaver registry value is reported (not changed). `--cpu-info` at the
  start and the end. The `--selftest` on the measured binary must PASS first. SASS md5 recorded.
- Cells as in §1–§6. Each cell runs its kernels in order and then reversed (A B … B A), and the value is
  the mean of the two pass medians. Runs: GPU 11; CPU 7 (5 at N ≥ 262144 all-pairs, 3 at N = 262144 for
  sets e and p1). GPU warm-up 300 ms; CPU warm-up 2 launches. Idle check between cells; a flagged cell is
  re-run, not scored.
- The script is copied before it is run and never edited while running; to stop it, kill the script
  process itself.
- Rule 8: GPU speedups vs the CPU are quoted against the best-tuned CPU configuration of the same session
  (over IV, tile, group, leaf, set, threads, schedule), and hybrid ratios against the best-tuned GPU-only
  configuration of the same cell.
