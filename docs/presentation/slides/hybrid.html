Split the work

Best gain over the GPU alone: +1.3 %; most cells 0.99–1.27× slower.

The trap we caught

The CPU-tree version looked 4–25 % faster. A GPU-only control that refits the old tree is just as fast (within 1.4 %).

The gain was never the CPU’s. Always ask: what is the control?

Dynamic scheduling: 37.8 G/s, +22 %. Equal work is not equal time.

CPU: Intel i5-13600K, 6 P-cores + 8 E-cores, with an AVX2 + FMA all-pairs and tree code, multithreaded. GPU vs CPU, best against best: 29–36× for all-pairs from 16,384 bodies, 18.3× for the tree at 1M. Two splits: hyb_bh gives a share of the bodies to the CPU; hyb_phase builds the tree on the CPU while the GPU computes forces. Neither beats the GPU alone; the best gain anywhere is 1.3 %. The trap: hyb_phase looked up to 25 % faster. But it reuses an older tree while the CPU builds the next one. A GPU-only kernel that does the same (bh_warp_refit) matches it within 1.4 %, so the speed-up is "refit instead of rebuild", not the CPU. And in the timing loop the bodies do not move, so the older tree costs nothing there; in a real 500-step run it costs 4–10 % more interactions. The CPU balancing lesson: an E-core does about 0.21 of a P-core's work. A static even split makes everyone wait for the E-cores, slower than not using them. Dynamic scheduling puts 78 % of the work on the P-cores and gains 22 %. Clean session: 438 runs, 70 of 82 predictions hit.
