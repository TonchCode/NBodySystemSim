How we kept the results honest. Before each measurement round we committed a file of predictions with ranges (docs/predictions/), then scored every item HIT or MISS in a committed scorecard. Misses stay in the report. Examples of being wrong, and what we learned: Block 64 removed the wave tail exactly as modelled but was 8 % faster, not 20 %: the model's per-block cost was too small. #6: we expected persistent queues to help; they were slower everywhere, and the diagnosis taught us that L1 locality matters more than balance. #7: called latency-bound from occupancy sweeps; Nsight Compute showed it is closer to balanced. An early draft said "Burtscher's 10× from sorting fails on Ada"; withdrawn, because his statement was about different code on different hardware. Other rules: every speedup is against the best-tuned baseline of the same session; tree rates are real interaction rates, not N²-equivalent; load-sensitive results were replicated at 0 % background load and the clean values are canonical. Platform caveat: all runs at the 272 W power cap, so faster kernels run at lower clocks. Docs: docs/predictions/*.md; 04-load-balancing.md header rules and §4.9 scorecards; 07-defence-guide.md §7.5.
