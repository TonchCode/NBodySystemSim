Conclusions

Four things we can say from the measurements

1 · All-pairs: SM level

Make enough work items (smaller blocks, q threads per body): 2.4–2.6× at small N, nothing once every SM is busy.

2 · Trees: inside the warp

Sorting is the first step (2×); the warp walk removes the rest (5.8×), even though it does more work.

3 · The hardware scheduler wins

Software queues balanced better and ran slower. Locality in L1 mattered more than balance.

4 · Memory decides the tree

Sorted tree: waiting on L2. Warp walk: 14× less memory traffic, compute-bound like all-pairs.

Four conclusions, each limited to what was measured, on this one GPU, at θ = 0.5. 1. For all-pairs the imbalance is entirely at SM level, fixed by creating the right number of work items. 2. For trees the dominant loss is inside warps. Sorting is necessary; the warp-union walk on top of it gives 5.8× best against best at 1M. 3. On sm_89 the hardware block scheduler is hard to beat: it is already a dynamic queue that keeps Morton-adjacent warps together. Better balance is not better performance when the kernel is bound by L1. 4. The profiler ties it together: the sorted tree waits on L2 (95 % throughput); the warp walk cuts memory traffic 14× and becomes compute-bound.
